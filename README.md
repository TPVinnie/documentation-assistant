# Local Documentation Intelligence Assistant

A local-first Retrieval-Augmented Generation (RAG) system that ingests a document collection and
answers natural-language questions with traceable citations, explicit abstention when evidence is
weak or missing, and transparent handling of versioned/contradictory sources.

Built for the "Local Documentation Intelligence Assistant" assignment. See `ARCHITECTURE.md` for
component/design details and `TECHNICAL_REPORT.md` for experiments, error analysis, and
limitations.

## Prerequisites

- Python 3.11+
- macOS/Linux/WSL (developed and tested on macOS)
- [Ollama](https://ollama.com) installed and running locally, with a model pulled (default:
  `llama3.2:3b`) — **only required for real generation**; all ingestion, retrieval, and automated
  tests run without it via the built-in mock generation provider (see below).
- ~2-3 GB free disk for Python dependencies (sentence-transformers pulls PyTorch).

## Local-first design

No document pack was supplied for this assignment, so a synthetic, clearly-labeled corpus is
generated by `scripts/make_corpus.py` (see `data/SAMPLE_CORPUS_NOTES.md`) — no confidential
documents are included or required.

Everything runs locally by default:

| Component | Backend | Requires network/API key? |
|---|---|---|
| Embeddings | `sentence-transformers/all-MiniLM-L6-v2` (local) | No |
| Vector index | ChromaDB, persisted on disk | No |
| Lexical index | BM25 (`rank_bm25`), persisted on disk | No |
| Reranker | `cross-encoder/ms-marco-MiniLM-L-6-v2` (local) | No |
| Generation | Ollama (local server) | No — but Ollama must be running |
| Generation (offline/CI) | `mock` provider — deterministic, no model | No |

Set `DOCS_ASSISTANT_LLM_PROVIDER=mock` to run the entire system (including `/ask`) without Ollama
at all — this is what the automated test suite uses, so ingestion, retrieval, and tests never
require external credentials or a running model.

## Setup

```bash
cd documentation-assistant
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # defaults work out of the box; edit if needed
```

Pull an Ollama model if you want real (non-mock) generation:

```bash
ollama pull llama3.2:3b
```

Or run the whole thing in one command: `bash scripts/setup.sh` (venv + deps + `.env` + corpus).

## Generate the sample corpus

No document pack was provided for this assignment; this generates the synthetic one described in
`data/SAMPLE_CORPUS_NOTES.md`:

```bash
python scripts/make_corpus.py
```

## Indexing

```bash
python scripts/ingest.py
# or, to index a different folder:
python scripts/ingest.py --path /path/to/other/documents
```

This prints a JSON processing report (files indexed/updated/unchanged/skipped/failed, with a
message for each). Re-running is incremental — unchanged files are skipped by checksum; only
added/modified files are re-embedded, and removed files are pruned from the index. The persisted
index lives under `data/index/` (Chroma + BM25 + SQLite metadata) and can be deleted at any time
to force a full rebuild.

## Running

### Using the web UI

1. Make sure the corpus is indexed at least once (see "Indexing" above) and, if you want real
   (non-mock) answers, that Ollama is running (`ollama serve`, or the Ollama desktop app) with a
   model pulled.
2. Start the API server:

   ```bash
   cd documentation-assistant
   source .venv/bin/activate
   uvicorn app.api.main:app --reload
   ```

3. Open **http://localhost:8000/ui** in a browser.

What you'll see:

- **Ingestion** — buttons to re-run ingestion and view the processing report, check `/status`
  (file/chunk counts, feedback summary), and check `/health` (embedding model, vector store,
  reranker, LLM).
- **Ask a question** — a text box, a configuration picker (`baseline` / `improved_a` /
  `improved_b`), and optional filters (category, file name).
- **Answer** — the generated answer; citations (with a "superseded" badge where relevant);
  evidence-quality and conflict-signal indicators; 👍/👎 feedback buttons; and expandable panels
  for the raw retrieved evidence (with dense/lexical/fused/rerank scores) and per-stage timings.

Try, for example, *"How long must log data be retained?"* or *"What is the API rate limit?"* (the
latter surfaces the corpus's built-in cross-document contradiction).

With a real (non-mock) Ollama backend, each answer typically takes 15-40 seconds to generate on
CPU-only hardware — that's expected local-inference latency, not a hang (see "Slow generation" in
Troubleshooting below). Set `DOCS_ASSISTANT_LLM_PROVIDER=mock` before starting the server for
instant, deterministic answers while just exploring the UI.

Other useful links once the server is running:

- API docs (interactive): http://localhost:8000/docs
- Health check: http://localhost:8000/health

### Using the CLI instead

Use the CLI test client directly, without starting a server:

```bash
python scripts/ask.py "How long must log data be retained?"
python scripts/ask.py "What is the API rate limit?" --config baseline --show-evidence
```

### API endpoints (FR-15)

| Method | Path | Purpose |
|---|---|---|
| POST | `/ingest` | Run ingestion, return the processing report |
| GET | `/status` | Index/file/chunk counts, feedback summary |
| GET | `/health` | Component health (vector store, embeddings, reranker, LLM) |
| POST | `/ask` | Ask a question; returns answer, citations, evidence, timings |
| GET | `/evidence/{chunk_id}` | Full text + metadata of one cited/retrieved chunk |
| POST | `/feedback` | Record useful/not-useful + optional reason for an answer |

## Evaluation

```bash
python scripts/evaluate.py
# or a subset:
python scripts/evaluate.py --configs baseline improved_b
```

This runs all (or selected) configurations from `app/evaluation/configs.py` over the 43-question
labeled dataset at `data/evaluation/eval_questions.jsonl`, and writes:

- `artifacts/results_<config>.json` — full per-question run log + metrics for that configuration
- `artifacts/results_comparison.json` — condensed side-by-side metric comparison

See `TECHNICAL_REPORT.md` for the results, how each metric is computed, what it does and doesn't
prove, and why the final configuration was selected.

By default, evaluation uses the configured `DOCS_ASSISTANT_LLM_PROVIDER` (Ollama, if set), which
means end-to-end evaluation latency is dominated by local LLM inference (tens of seconds per
question on CPU-only hardware) — retrieval-only metrics are unaffected by this and are fast. Set
`DOCS_ASSISTANT_LLM_PROVIDER=mock` for a fast, fully-deterministic run of the pipeline mechanics
(citations, abstention gating, retrieval metrics) without waiting on model inference.

## Testing

```bash
pytest
# with coverage:
pytest --cov=app
```

Test suite (all use the `mock` LLM provider — no Ollama or network required):

- `tests/unit/` — chunking, rank fusion, injection detection, citation validation, abstention
  policy, document-metadata/version resolution, query processing, evaluation metrics/dataset
- `tests/integration/` — ingestion pipeline (parsing, incremental updates, duplicates, version
  resolution, malformed files, file-size limits), the retrieval pipeline (filters, hybrid vs.
  dense-only, version ranking), and the evaluation runner, all against a real (tmp) Chroma/BM25/
  SQLite index
- `tests/e2e/` — full ingest → retrieve → generate → cite round trip (including a regression test
  for the conversation-follow-up abstention fix in `TECHNICAL_REPORT.md` §5), and a smoke test
  through the actual FastAPI app

## Configuration

All tunables are environment variables (see `.env.example`), loaded via `app/config.py`. Key ones:

- `DOCS_ASSISTANT_LLM_PROVIDER` — `ollama` or `mock`
- `DOCS_ASSISTANT_OLLAMA_MODEL` — e.g. `llama3.2:3b`, `qwen3:8b`, `gpt-oss:20b`
- `DOCS_ASSISTANT_USE_RERANKER` — `true`/`false`
- `DOCS_ASSISTANT_TOP_K_*`, `DOCS_ASSISTANT_MAX_CONTEXT_CHARS` — retrieval/context sizing
- `DOCS_ASSISTANT_MIN_EVIDENCE_SCORE`, `DOCS_ASSISTANT_MIN_CITATION_COVERAGE` — abstention
  thresholds (heuristic, documented in `app/generation/abstention.py`)
- `DOCS_ASSISTANT_MAX_FILE_SIZE_MB` — ingestion file-size limit (default 25 MB)

Retrieval *configurations* (chunking strategy + hybrid/rerank on/off + top-k) are separate from
these environment defaults and are defined as named presets in `app/evaluation/configs.py`
(`baseline`, `improved_a`, `improved_b`); `/ask` and `scripts/ask.py` accept a `config_name` to
select one at request time.

## Troubleshooting

- **"Ollama request failed" / generation errors**: confirm `ollama serve` is running and the model
  in `DOCS_ASSISTANT_OLLAMA_MODEL` has been pulled (`ollama list`). The system does not crash when
  Ollama is unreachable — `/ask` returns a clear "generation model is currently unavailable"
  message with retrieved evidence still attached; `/health` reports `llm.ok: false`.
- **Slow generation**: local CPU inference with a 3B model can take 10-40+ seconds per answer on
  modest hardware; this is expected for a local-first setup, not a bug. Use
  `DOCS_ASSISTANT_LLM_PROVIDER=mock` to iterate on retrieval/citation logic without waiting on it.
- **Chroma telemetry error in logs**: an old chromadb/posthog version mismatch; pinned in
  `requirements.txt` (`posthog<3.0`) — if you see it anyway, re-run `pip install -r requirements.txt`.
- **Index looks stale/wrong**: delete `data/index/` and re-run `python scripts/ingest.py` for a
  clean rebuild; this is always safe since the index is fully derived from `data/sample_documents/`.
- **A file was silently skipped**: check the `/ingest` (or `scripts/ingest.py`) processing report —
  every skip/failure includes a human-readable reason (unsupported type, empty, encrypted,
  corrupted, oversized, or duplicate-of-another-file).

## Known limitations

See `TECHNICAL_REPORT.md` ("Limitations" and "Error analysis") for the full list, including two
real bugs found and fixed during evaluation (a retrieval-score-scale mismatch that caused
over-abstention, and a soft-refusal metric that missed a common phrasing) and several open items.
In short: contradiction/conflict detection relies on prompted LLM behavior plus a coarse "multiple
documents contributed" signal, not real semantic entailment; answer-quality metrics (groundedness,
completeness) are lexical-overlap heuristics, not an LLM-judge or human evaluation; and the
injection guard is regex-based, so it will miss novel phrasings by design (see
`app/generation/injection_guard.py`).

## Assumptions

- No document pack was supplied; a synthetic, clearly-labeled corpus stands in for it (see
  `data/SAMPLE_CORPUS_NOTES.md`), per the assignment's allowance for a labeled synthetic subset.
- "Local-first" is interpreted as: no external API keys required for the system to run end-to-end,
  including automated tests (via the `mock` LLM provider); Ollama is used for real generation
  since it runs entirely on the local machine.
- Metadata filtering (FR-08) is applied at dense/lexical query time rather than strictly after
  fusion, so a narrow filter can't be starved out by a top-k cut before fusion ever sees it
  (documented trade-off in `ARCHITECTURE.md`).
- Superseded-version documents are retrievable (not filtered out entirely) so that version/conflict
  questions and explicit historical queries still have evidence to work with; they are penalized in
  ranking and explicitly flagged in citations and prompt instructions instead.
- The suggested layout's top-level `config/` folder is instead `app/config.py` (a single
  `pydantic-settings` module) since there was no need for multiple config files; every other
  suggested directory (`ingestion/`, `indexing/`, `retrieval/`, `reranking/`, `generation/`,
  `evaluation/`, `api/`, `ui/`, `data/`, `tests/`, `scripts/`, `artifacts/`) is present as named.
